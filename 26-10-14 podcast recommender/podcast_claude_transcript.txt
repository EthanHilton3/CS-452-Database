  Introduction
  Vector databases are currently widely used in industry to solve problems such
  as similarity and semantic search, retrieval augmented generation, image
  search, recommendation systems, natural language processing (NLP), and
  computer vision.

  The basic idea is that we some type of neural network to compress salient
  information found in high dimensional data, such as large documents or
  images, into a fixed size low-dimensional vector. Vectors refer to
  mathematical representations of data points in multidimensional space. They
  are typically arrays or lists of numerical values that capture an entity's
  essential features or attributes. In machine learning and data science,
  vectors encode information in a way that enables efficient computation and
  analysis.

  Recent advances in vector DBs allow us to perform linear-algebra computations
  on vector spaces with raw SQL code. In this lab we will use pgvector, which
  is a PostgreSQL extension that provides powerful functionalities for working
  with vectors in high-dimensional space. It introduces a dedicated data type,
  operators, and functions that enable efficient storage, manipulation, and
  analysis of vector data directly within the PostgreSQL database.

  One of the main challenges and learning opportunities in this project will be
  transforming and moving data into PostgreSQL.

  Database Schema
  We will create a database with two tables: podcast and segment:

  podcast

  PK: id
  The unique podcast id found in the huggingface data (i,e., TRdL6ZzWBS0  is
  the ID for Jed Buchwald: Isaac Newton and the Philosophy of Science | Lex
  Fridman Podcast #214)
  title
  The title of podcast (ie., Jed Buchwald: Isaac Newton and the Philosophy of
  Science | Lex Fridman Podcast #214)
  segment

  PK: id
  the unique identifier for the podcast segment. This was created by
  concatenating the podcast idx and the segment index together (ie., "0;1") is
  the 0th podcast and the 1st segment
  This is present in the as the "custom_id" field in the `embedding.jsonl` and
  batch_request.jsonl files
  start_time
  The start timestamp of the segment
  end_time
  The end timestamp of the segment
  content
  The raw text transcription of the podcast
  embedding
  the 128 dimensional vector representation of the text
  FK: podcast_id
  foreign key to podcast.id

  "Isn't Postgres just a language like SQL?"

  No, and the difference matters. SQL is the language. Postgres is a program: a
  database server that understands SQL. It's the same relationship Python code
  has to the python interpreter that runs it.

  "Running Postgres" means starting a process that:
  - keeps data in files on disk,
  - listens on network port 5432 for connections,
  - takes SQL from clients, runs it, and sends back results.

  Your Python script is one of those clients. It connects to localhost:5432 with
  the username and password in .env, then sends SQL as strings. SQLite, which
  you used in the last lab, works differently: it's just a library reading a
  single file, with no server. Postgres is how real production databases run.

  pgvector is a plugin for Postgres. It adds a vector(128) column type and the
  distance operators (<-> and friends), so Postgres can do the similarity math
  itself.

  Why Docker?

  Installing Postgres on Windows, then compiling pgvector into it, is a pain.
  Docker skips all that.

  - Image: a packaged snapshot of a small Linux system with software already
    installed. pgvector/pgvector:pg17 holds Debian Linux, Postgres 17, and
    pgvector, already set up.
  - Container: a running instance of an image, a bit like a lightweight virtual
    machine. Images are to containers what classes are to objects.

  What my command did:
  docker run --name pgvector -e POSTGRES_PASSWORD=... -p 5432:5432 -d
  pgvector/pgvector:pg17
  - downloaded the image,
  - started a container from it and named it pgvector,
  - set the database password,
  - -p 5432:5432 connected your Windows port 5432 to the container's port 5432,
    so localhost:5432 reaches Postgres,
  - -d runs it in the background.

  The benefits: it's isolated, it's the same setup everyone in the class gets,
  and deleting it leaves nothing behind on your machine. Your data stays inside
  the container until you remove it. You can stop and start it from Docker
  Desktop.

  The virtual environment (.venv)

  Without one, pip install puts packages into your one global Python, which
  every project shares. Then project A wants pandas 2.x, project B wants 1.x,
  and they collide.

  A venv is a folder holding a private copy of the Python setup with its own
  packages. Here's what I ran:
  1. python -m venv .venv created the folder .venv/, with its own python.exe and
     an empty package directory.
  2. .venv/Scripts/python -m pip install -r requirements.txt installed the
     packages listed in requirements.txt into that folder only.

  "Activating" it (.venv\Scripts\activate) just makes python in that terminal
  point to the venv's copy. requirements.txt is the recipe, so anyone can
  rebuild the same environment. That's why the folder itself is gitignored.

  The packages:
  - psycopg2 lets Python talk to Postgres.
  - pandas handles dataframes.
  - datasets downloads the HuggingFace podcast data.
  - python-dotenv reads .env so your password isn't hard-coded.

  How it becomes a recommender

  1. Already done by your professor: each transcript segment went through
     OpenAI's embedding model, which turned it into 128 numbers. Text with
     similar meaning lands at nearby points in that 128-dimensional space.
  2. db_build.py: creates the empty tables.
  3. db_insert.py: fills them with podcasts, segments, and their vectors.
  4. db_query.py: for a recommendation, take one segment's vector and ask
     Postgres for the rows with the smallest distance to it:
  ORDER BY embedding <-> (that segment's embedding) LIMIT 5
     Those nearest neighbors are your "similar segments." Average all of an
     episode's vectors and you get one point per episode, which gives you
     episode recommendations.

  The recommender is just "find the nearest points." The embeddings carry the
  meaning, and Postgres does the search.

> give me an anology and short explanation to explain the differnece of images

● Analogy: an image is a recipe, a container is a dish cooked from it.

> what are python pacjages?

● A package is code someone else wrote and published so you can import it
  instead of writing it yourself. It's like a library in Java (a .jar) or a C++
  library you link against.

  - Built in: some modules come with Python itself, like json, os, and io. Those
    need no install.
  - Third-party: everything else, like pandas, psycopg2, and datasets, lives on
    PyPI (pypi.org), Python's public package registry.
  - pip downloads a package from PyPI, plus any packages it depends on, and puts
    the files in a site-packages folder. That folder sits inside .venv when you
    use a venv, or in your global Python otherwise.
  - import pandas makes Python look through that site-packages folder for the
    code.

  So pip install pandas is roughly "download someone's dataframe library and put
  it where Python can find it." requirements.txt is just a list of those
  downloads.

> oh so its similar to how npm is a package manager for js?

● Yes, it's almost exactly the same idea:

  │ npm                │ pip                               │
  ├────────────────────┼───────────────────────────────────┤
  │ npmjs.com registry │ PyPI                              │
  ├────────────────────┼───────────────────────────────────┤
  │ package.json       │ requirements.txt                  │
  ├────────────────────┼───────────────────────────────────┤
  │ node_modules/      │ .venv/ (its site-packages folder) │
  └────────────────────┴───────────────────────────────────┘

  The one real difference is that npm isolates each project by default: every
  project gets its own node_modules. pip installs into your global Python unless
  you make a venv yourself. So a venv basically gives Python the per-project
  node_modules behavior that npm has built in.

> what is the serial data type in postgres?

● SERIAL is an auto-incrementing integer. If you leave the column out of an
  INSERT, Postgres fills in the next number for you: 1, 2, 3, ...

  CREATE TABLE example (
      id SERIAL PRIMARY KEY,
      name TEXT
  );
  INSERT INTO example (name) VALUES ('a'), ('b');   -- ids 1 and 2 assigned
  automatically

  Under the hood it's an INTEGER column plus a sequence, a counter object that
  hands out the next value. The modern standard way to write the same thing is
  INTEGER GENERATED ALWAYS AS IDENTITY. BIGSERIAL is the 64-bit version.

  You don't need it for this project. SERIAL is for when your table has to
  invent IDs. Both of your tables already get their IDs from the data:
  TRdL6ZzWBS0 and 89:115. Those aren't sequential numbers. They're the real
  identifiers, and you'll use them to join tables and look up rows, as in "find
  segments similar to 267:476." So those primary keys should be columns that
  store the given values as they are. Which type fits values like those?

> whats a b-tree index?

● A B-tree is a balanced search tree. Think of a binary search tree where each
  node holds many sorted keys and has many children instead of 2. It's built to
  work well on disk:

                   [ 4:200 | 89:500 ]
                /         |          \
     [0:1 … 4:199]  [4:201 … 89:499]  [89:501 … 345:999]
          ↓               ↓                   ↓
       rows on disk    rows on disk        rows on disk

  - Why many keys per node: each node is sized to fill one disk page (8 KB in
    Postgres). Reading from disk is slow, so you want each read to cut the
    search space as much as possible. With hundreds of keys per node, a million
    rows is only 3–4 levels deep.
  - Balanced: every leaf is at the same depth, and inserts or deletes keep it
    that way. A lookup is always O(log n).
  - Sorted: the keys stay in order, so it handles =, <, >, BETWEEN, and ORDER BY
    on that column.

  What it does for you: WHERE id = '267:476' follows a few nodes down the tree
  instead of scanning all 832k rows. That's a full table scan versus a handful
  of page reads.

  Why it won't help with the vector queries: a B-tree depends on keys being
  sortable in one line. Vectors with 128 dimensions have no meaningful single
  sort order, and "closest to this point" isn't a less-than/greater-than
  question. That's why vector search needs a different index type, like HNSW,
  the one you'll try in the "going further" part.

  How does a b-tree fit in exactly to this project?

● What that sentence means

  Without an index, Postgres stores rows in no particular order. Finding
  '267:476' means reading every row and checking each one's id. That's a full
  table scan, roughly 832k comparisons and hundreds of MB read from disk.

  With the B-tree on id, Postgres starts at the root and asks at each level
  which child could contain '267:476', just like a binary search, with only 3–4
  steps total. The leaf it reaches says where that row is stored on disk, and
  Postgres goes straight there.

  Where it shows up in this project

  1. The first step of every query. Each of Q1–Q5 begins with "get the embedding
  of segment X":
  SELECT embedding FROM segment WHERE id = '267:476'
  That's an exact lookup on the primary key, so segment_pkey makes it nearly
  instant.

  2. Joins to get the podcast title. Q1–Q4 return the podcast name, so every
  result row joins segment.podcast_id = podcast.id. That join looks up
  podcast.id in podcast_pkey.

  3. During the insert. For each of the 832k rows you load, Postgres has to
  check:
  - Primary key: is this id already in the table? It checks the B-tree.
  - Foreign key: does this podcast_id exist in podcast? It checks the B-tree on
    podcast.id.

  Without those indexes, each check would be its own scan, and loading the data
  would take forever. This is also why the order matters: the foreign key check
  fails if podcast is still empty.

  Where it doesn't help

  The main part of each query, ORDER BY embedding <-> X LIMIT 5, can't use a
  B-tree at all, as I mentioned. Postgres still computes the distance to all
  832k vectors. That's the slow part, and it's what HNSW is meant to speed up.

  See it yourself

  After loading the data, put EXPLAIN ANALYZE in front of a query:
  EXPLAIN ANALYZE SELECT * FROM segment WHERE id = '267:476';
  You'll see Index Scan using segment_pkey and a time in fractions of a
  millisecond. Try WHERE content = '...', a column with no index, and you'll see
  Seq Scan and a much larger time. That before-and-after is a strong learning
  log entry.

> tell me about pd.merge

● pd.merge is pandas' version of a SQL JOIN. It combines two DataFrames into one
  by matching rows on a shared column.

  merged = pd.merge(left_df, right_df, on="key_column", how="inner")
  # same thing, method style:
  merged = left_df.merge(right_df, on="key_column", how="inner")

  The SQL equivalent:
  SELECT * FROM left_df JOIN right_df ON left_df.key_column =
  right_df.key_column

  on: which column to match on

  The column has to exist in both DataFrames with the same name. If the names
  differ, use left_on="a", right_on="b".

  how: what to do with rows that don't match

  ┌────────────────┬───────────────┬───────────────────────────────────────┐
  │      how=      │     SQL       │                 Keeps                 │
  │                │  equivalent   │                                       │
  ├────────────────┼───────────────┼───────────────────────────────────────┤
  │ "inner"        │ INNER JOIN    │ Only IDs found in both                │
  │ (default)      │               │                                       │
  ├────────────────┼───────────────┼───────────────────────────────────────┤
  │ "left"         │ LEFT JOIN     │ Every left row; missing right values  │
  │                │               │ become NaN                            │
  ├────────────────┼───────────────┼───────────────────────────────────────┤
  │ "right"        │ RIGHT JOIN    │ Every right row                       │
  ├────────────────┼───────────────┼───────────────────────────────────────┤
  │ "outer"        │ FULL OUTER    │ Everything from both                  │
  │                │ JOIN          │                                       │
  └────────────────┴───────────────┴───────────────────────────────────────┘

  A small example

  a = pd.DataFrame({"id": ["1:0", "1:1", "1:2"], "content": ["hi", "there",
  "you"]})
  b = pd.DataFrame({"id": ["1:1", "1:0", "1:3"], "embedding": [[0.2], [0.1],
  [0.9]]})

  pd.merge(a, b, on="id")
  #     id content embedding
  # 0  1:0      hi     [0.1]
  # 1  1:1   there     [0.2]
  Order doesn't matter: rows are matched by key, not by position. 1:2 and 1:3
  have no partner, so an inner join drops them.

  Why the row-count check matters

  - Fewer rows than you started with: some IDs didn't match, so some segments
    would be missing their embedding.
  - More rows: an ID appears more than once on one side, and every combination
    got joined.

  pandas can check this for you:
  merged = pd.merge(a, b, on="id", validate="one_to_one")   # raises an error if
  any id is duplicated

  For your project, write the merge of doc_df and emb_df, pick a how, and check
  that you still have 832,839 rows. Since both sides have exactly that count,
  which how you choose only matters if the IDs don't line up. Use validate to
  find out.

● Yes, it's the same pattern as db_build.py, plus one new step. A SELECT returns
  rows, so after execute you have to fetch them:

  conn = psycopg2.connect(CONNECTION)

  cursor.execute(Q1)
  rows = cursor.fetchall()     # list of tuples, one tuple per result row

  for row in rows:

  conn.close()

  keeps the output tidy:

  def run(name, sql):
      cursor.execute(sql)
      print(f"\n=== {name} ===")
      for row in cursor.fetchall():
          print(row)

  run("Q1", Q1)
  run("Q2", Q2)

  To print the column names too, cursor.description holds them after an execute:
  [col[0] for col in cursor.description]. Or pass the rows to
  pd.DataFrame(rows, columns=...) for a table-style printout.

  The main issue: averaging distances instead of vectors

  Both queries compute AVG(distance): the distance from the query to each
  segment, then the average of those distances. The hint says to average the
  embedding vectors: build one average vector per episode, then take one
  distance to it.

  The two give different answers. In 1D: an episode has two segments, at -1 and
  +1, and your query is at 0.
  - Average of distances: (1 + 1) / 2 = 1
  - Distance to the average vector: the average is 0, so the distance is 0

  The average-distance version penalizes episodes that cover lots of topics,
  even when the query sits right at the episode's center. In SQL, the difference
  is which side of <-> the AVG goes on:

  AVG(s.embedding <-> query_vec)     -- yours: average of 2000+ distances
  AVG(s.embedding) <-> query_vec     -- intended: one distance to the episode's
  average vector

  pgvector's AVG() works directly on vector columns and returns a vector.

  Q5 fix: move AVG inside, around s.embedding only. The rest of your query
  (GROUP BY, ORDER BY, LIMIT) can stay as it is.

  Q6: the self-join compares billions of pairs

> explain to me the plan for q6 again
● Q6 is Q5 with a different query vector.

  In Q5, the "query point" is one segment's vector:
  (SELECT embedding FROM segment WHERE id = %(seg_id)s)

  In Q6, the query is a whole episode, so the query point is that episode's
  average vector: all of Balaji's segments averaged into one 128-number vector.
  Everything else works as in Q5.

  The plan

  Step 1: build the query vector. Average Balaji's segments:
  (SELECT AVG(embedding) FROM segment WHERE podcast_id = %(podcast_id)s)
  This returns one vector, the center of that episode.

  Step 2: build one average vector per other episode. Same as your Q5:
  FROM segment s JOIN podcast p ...
  GROUP BY p.id, p.title        →  AVG(s.embedding) for each of the 346 episodes

  Step 3: exclude Balaji's own episode. Otherwise it would come back as #1 with
  distance 0. You exclude a podcast here rather than a segment, so filter on
  s.podcast_id.

  Step 4: compare and rank. The distance from each episode's average (step 2) to
  Balaji's average (step 1), ORDER BY distance, LIMIT 5.

  The shape, compared with Q5

  Q5:  AVG(s.embedding) <-> (one segment's vector)              WHERE s.id
    != that segment
  Q6:  AVG(s.embedding) <-> (AVG of the query episode's vectors)  WHERE
  s.podcast_id != that episode

  There's only one segment table in the main FROM, with no self-join. That's
  what makes it fast: it scans the 832k rows once to build the 346 averages,
  plus once more for the subquery, instead of comparing every segment pair.

  Get Q5 working first with AVG in the right place. Q6 should then be about a
  two-line change.
