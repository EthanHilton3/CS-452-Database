● Redis is a dictionary that lives on a server. Every key maps to a value, and
  any process connected to the server can read or change it. That's how the web
  server and the worker share data without talking to each other directly.

  Each value has a type. This project uses two:
  - string: one value, like a Python str
  - list: an ordered sequence, like a Python list

  The commands, one at a time

  Command: RPUSH q a b c
  What it does: Adds a, b, c to the right end (tail) of the list at key q.
  Creates the list if it doesn't exist.
  Returns: (integer) 3, the new length
  Python equivalent: r["q"].extend(["a","b","c"])
  ────────────────────────────────────────
  Command: LRANGE q 0 -1
  What it does: Reads items from index 0 to the last one. -1 means "last", same
  as Python. Doesn't change the list.
  Returns: a, b, c
  Python equivalent: r["q"][0:]
  ────────────────────────────────────────
  Command: LPOP q
  What it does: Removes and returns the item on the left end (head).
  Returns: "a"
  Python equivalent: r["q"].pop(0)
  ────────────────────────────────────────
  Command: LRANGE q 0 -1
  What it does: Reads again, to show a is gone
  Returns: b, c
  Python equivalent:
  ────────────────────────────────────────
  Command: SET result:123 "hello"
  What it does: Stores a string at key result:123. Overwrites whatever was
  there.
  Returns: OK
  Python equivalent: r["result:123"] = "hello"
  ────────────────────────────────────────
  Command: GET result:123
  What it does: Reads that string. Returns (nil) if the key doesn't exist.
  Returns: "hello"
  Python equivalent: r.get("result:123")
  ────────────────────────────────────────
  Command: TYPE q
  What it does: Tells you what type of value a key holds
  Returns: list
  Python equivalent: type(r["q"])
  ────────────────────────────────────────
  Command: TYPE result:123
  What it does: Same
  Returns: string
  Python equivalent:
  ────────────────────────────────────────
  Command: DEL q result:123
  What it does: Deletes those keys
  Returns: (integer) 2, the number deleted
  Python equivalent: del r["q"], r["result:123"]

  Things that trip people up

  - The L in a command name doesn't always mean "left". In LPOP and RPUSH, L and
    R mean left and right. In LRANGE and LTRIM, the L just means List.
  - Push on the right, pop on the left, and the list works as a FIFO queue.
    First in, first out, like a line at a store.
  - The colon in result:123 means nothing to Redis. It's only a naming habit for
    grouping keys. To Redis, a key is just a string.
  - Reading and removing are different. LRANGE reads without removing. LPOP
    reads and removes in one step, and Redis runs it as one uninterruptible
    operation. Keep this in mind for Deliverable 4.

  One more command you'll see in the project

  LTRIM q 2 -1 keeps only the items from index 2 to the end and throws away the
  rest. In effect, it deletes the first 2 items.

  The worker in run_model_server.py
  (26-11-02%20redis%20concurrency/run_model_server.py) uses LRANGE to read a
  batch and later uses LTRIM to remove it. Think about this for later: what
  could happen if two workers do that at the same time?

  Why nothing printed

  1. The for loop starts 20 threads, one every 0.05 s, so it finishes in about 1
     second.
  2. Without the sleep(300), the main thread hits the end of the file right
     after that.
  3. Python doesn't wait for daemon threads when the program exits. It kills
     them on the spot.
  4. Each request takes at least 2 seconds (we saw that in the monitor). So all
     20 threads were still waiting for their HTTP response when they were
     killed, and none of them got to print.

  A daemon thread is a background helper. Python treats it as not important
  enough to keep the program running. A normal thread (daemon=False, the
  default) does keep the program running until it finishes.

  Check Terminal B, the worker

> what does the join function do in this situationa dn how cna i use it?

● t.join() means: "Main thread, stop here and wait until thread t has finished."
  Once t finishes, the main thread moves on to the next line. If t is already
  done, join() returns immediately.

  How it works

  Here's a small example that isn't your stress test:

  from threading import Thread
  import time

  def work(n):
      time.sleep(n)          # pretend this is a slow HTTP request
      print(f"worker {n} done")

  t1 = Thread(target=work, args=(2,))
  t2 = Thread(target=work, args=(1,))
  t1.start()                 # both start running right away, in parallel
  t2.start()

  t1.join()                  # main waits here until t1 finishes (~2 s)
  t2.join()                  # t2 already finished at 1 s, so this returns
  immediately
  print("all done")          # always prints LAST

  Output:
  worker 1 done
  worker 2 done
  all done

  The timeline:
  time:   0s        1s        2s
  t1:     |=====================|  done
  t2:     |==========|  done
  main:   start,start, t1.join() .. waiting .. | t2.join() returns at once |
  "all done"

  The total time is about 2 s, not 3 s. The threads still run in parallel,
  because join() doesn't make them take turns. It only makes the main thread
  wait at that point.

  Three things people get wrong

  1. Call join() after you've started all the threads, not right after each
     start(). t.start(); t.join() inside the loop would wait for each request
     before starting the next one, so the threads would run one at a time and
     the stress test would stop being a stress test.
  2. Join every thread. If you only join the last thread you started, some
     earlier ones might still be running when the program exits. In your case,
     they're daemon threads, so they'd get killed.
  3. The order you join in doesn't matter. You end up waiting for the slowest
     thread either way.

  Using it in your stress test

  The pattern is:
  1. Before the loop, make an empty list.
  2. Inside the loop, after t.start(), add t to the list.
  3. After the loop, go through the list and call join() on each thread.
  4. Delete time.sleep(300).

  That's about 4 lines. Write it, run it, and paste it here.

> why do i have to add the thread after t.start() why cant i add it right after
  the Thread constrcuotr?

● You can. It makes no difference here, and I shouldn't have said "after."

  The list doesn't store a copy of the thread. It stores a reference to the same
  Thread object. So whether you append it before or after start(), the list
  points to the same thread, and join() will work on it later.

  The only rule is about join(), not the list: you can only join a thread that
  has been started. Calling join() on a thread that was never started raises
  RuntimeError: cannot join thread before it is started.

  In your loop every thread gets started right away, so both of these work the
  same:
  t = Thread(...)
  threads.append(t)   # fine
  t.start()
  t = Thread(...)
  t.start()
  threads.append(t)   # also fine

  Use whichever reads better to you.

  What happened

  Here's a small example of the race. Assume [1 2 3] were queued when both
  workers polled:
  queue:  [1 2 3]
  A: LRANGE → [1 2 3]                    B: LRANGE → [1 2 3]       ← same
  images, read twice
          ...while both are running ResNet (~1–2 s), requests 4, 5, 6, 7
  arrive...
  queue:  [1 2 3 4 5 6 7]
  A: SET 1,2,3   LTRIM 3 -1 → [4 5 6 7]                          ← correct
  B: SET 1,2,3 again                                              ← DUPLICATE
  results → orphan keys
  B: LTRIM 3 -1 → [7]                                             ← deletes 4,
  5, 6 unprocessed → LOST
  There's one root cause behind both symptoms. Reading the queue (LRANGE) and
  removing from it (LTRIM) are two separate steps, about 2 seconds apart. In
  between, another worker can read the same items, and the queue can change.
  LTRIM removes "the first N items." It doesn't remove "the items I processed,"
  so it deletes whatever happens to be at the front by then.

  This pattern is called a check-then-act (or read-modify-write) race. It's the
  same kind of problem as two bank transactions both reading a balance of $100
  and each writing back $100 − $20.

  The fix is to make "take an item" a single atomic step. Then two workers can
  never get the same item, and nothing is deleted that hasn't been taken.

● Yes, you've got it, including the key detail that LTRIM removes by position
  and not by identity.

  Is LPOP atomic? Yes. Redis runs commands one at a time on a single thread.
  While one command is running, no other client's command can run in between. So
  any single Redis command is atomic:
  - LPOP image_queue 32 reads and removes up to 32 items in one indivisible
    step.
  - If two workers send LPOP at the same moment, Redis runs one, then the other.
    The second one gets whatever is left, so they can never get the same item.

  The catch is that atomicity applies to one command, not to a sequence of
  commands. Your bug came from LRANGE and LTRIM being two commands with 2
  seconds of work in between. Redis does have tools to make several commands
  atomic together (MULTI/EXEC transactions and Lua scripts), but you don't need
  them here, because one command does the whole job.

  There's a trade-off to note now, because Deliverable 4 asks about it next.
  With LPOP, the item leaves the queue before the work is done. If a worker
  crashes halfway through, that image is gone and its request hangs forever.
  You've traded "duplicate work and lost items" for "lost items only if a worker
  crashes." Delivering each job at most once is fine for now, and we'll come
  back to it.

  key. Web servers share nothing except Redis, and they never touch each other's
  keys, so there's no read-then-act gap like the one the workers had.

  One practical note: to actually run several, you'd put them on different ports
  behind a load balancer.

  Q2. UUIDs: correct, here are the numbers

  - 2¹²² ≈ 5.3 × 10³⁶ possible IDs.
  - By the birthday problem, you'd need about 2.7 × 10¹⁸ IDs before there's a
    50% chance of even one collision. At a billion requests per second, that
    takes about 86 years.
  - The realistic risk is a bad random source, for example cloned VMs starting
    with the same seed. uuid4() uses the operating system's secure random
    generator (os.urandom), so that isn't a concern here.

  Q3. Notifications: right about conflicts, wrong about scaling

  Conflicts: there aren't any. Each request subscribes to a channel named after
  its own UUID, so server #1 never receives server #2's event.

  Scaling has real costs:
  1. KEA turns on events for every change to every key. Each RPUSH, LPOP, SET
     and DEL publishes events, including all the queue traffic, even though
     nobody cares about most of them.
  2. psubscribe matches by pattern. For every event, Redis checks it against
     every pattern subscription. With 10,000 waiting requests, that's 10,000
     pattern checks for each key change: O(events × subscribers). Plain
     SUBSCRIBE to an exact channel name is a hash lookup instead, which costs
     about the same no matter how many subscribers there are.
  3. There's one pub/sub connection per waiting request. 10,000 waiting requests
     means 10,000 open connections. The better design is one subscriber
     connection per web server, which hands each event to whichever request
     thread is waiting for it.
  4. Notifications are fire-and-forget. If a subscriber isn't connected at the
     moment the event fires, the event is gone. This is the "missed
     notification" question in Deliverable 5.

  Q4. Crashed worker: that's the right design, with one fix

  What you described is the standard reliable queue pattern. It has a flaw
  you've already seen, though: "copy it to the working list, then pop it" is two
  steps, so it has a gap just like LRANGE and LTRIM did. If the worker crashes
  between the two steps, the item exists in both places.

  The fix is again a single atomic command:
  - Claim: LMOVE image_queue processing LEFT RIGHT moves the item to the
    processing list in one atomic step.
  - Acknowledge: after SET-ing the result, LREM processing 1 <item> removes it
    from the processing list.
  - Recover: a monitor process re-queues items that have been stuck too long. A
    list doesn't record when an item arrived, so record the claim time too. The
    usual way is a sorted set whose score is the timestamp, which lets the
    monitor ask for everything older than 30 s in one query.
  - What production systems use: Redis Streams with consumer groups have all of
    this built in. XREADGROUP claims, XACK acknowledges, and XAUTOCLAIM takes
    over messages that have been idle too long.

  The trade-off: if the timeout is too short, a slow but still-running worker
  has its job re-queued, and the job runs twice. That's called at-least-once
  delivery. Here it's harmless, because classifying the same image twice gives
  the same result written to the same key; the operation is idempotent. The
  leftover duplicate result is what caused your orphan keys, and you'd fix that
  with SET key value EX 60, so results delete themselves after 60 s.

  The web server should also stop polling after a timeout, so the user gets an
  error instead of a request that never ends.

  Part 1: See notifications by hand (5 min)

  Notifications are Redis's pub/sub (publish/subscribe) system pointed at your
  own data. Once they're turned on, every time a key changes, Redis publishes a
  small message on a channel named after that key. Anyone subscribed to that
  channel gets the message right away.

  Terminal X (the listener):
  docker exec -it redis-cs452 redis-cli
  CONFIG SET notify-keyspace-events KEA
  CONFIG GET notify-keyspace-events
  SUBSCRIBE __keyspace@0__:demo
  KEA is three flags:
  - K publishes keyspace events. The channel is named after the key
    (__keyspace@0__:demo), and the message is the command that changed it (set).
  - E publishes keyevent events, the reverse: the channel is named after the
    command (__keyevent@0__:set), and the message is the key.
  - A means all command types: strings, lists, deletes, and so on.

  The @0 is database number 0, which is the REDIS_DB = 0 in your settings.

  After you run SUBSCRIBE, Terminal X is stuck listening. That's expected.

  Terminal Y (open another redis-cli):
  SET demo hello
  SET other world
  DEL demo
  Watch Terminal X. You should see set and then del show up the moment you run
  them, and nothing for other. That's the whole mechanism. The web server will
  subscribe to its own UUID's channel, so it hears only about its own result.

  Press Ctrl+C in X when you're done.

  How redis_logger.py (26-11-02%20redis%20concurrency/redis_logger.py) works

  Piece: SERVER = hostname:PID
  Why it's there: Both workers run on your laptop, so the hostname alone would
  make them look identical. The process ID tells them apart. On real separate
  machines, the hostname would differ too.
  ────────────────────────────────────────
  Piece: SCRIPT = basename(sys.argv[0])
  Why it's there: The main script that started the process, even when log() is
  called from inside an imported module.
  ────────────────────────────────────────
  Piece: sys.stdout.write(... + "\n")
  Why it's there: One write per entry. print() writes the text and the newline
  separately, so with many threads you'd get the jumbled output you saw in the
  stress test.
  ────────────────────────────────────────
  Piece: pipeline() with rpush + ltrim
  Why it's there: Sends both commands in one network round trip. redis-py also
  wraps a pipeline in MULTI/EXEC by default, so the two commands run as one
  atomic unit. That's the "make several commands atomic together" tool I
  mentioned earlier.
  ────────────────────────────────────────
  Piece: LTRIM logs -1000 -1
  Why it's there: Keeps the newest 1000 entries. This use of LTRIM is safe,
  unlike the worker's: dropping the oldest log entries is exactly what we want,
   whoever's entries they are.
  ────────────────────────────────────────
  Piece: try / except RedisError
  Why it's there: If Redis is down, the server keeps running and the entry still

  prints to the terminal. Logging should never be the thing that crashes a
  server.

  view_logs.py (26-11-02%20redis%20concurrency/view_logs.py) prints the shared
  timeline. python view_logs.py <uuid> shows one request's path across every
  process. That's the basic idea behind distributed tracing, and it's the
  feature to highlight in your write-up.

  9. Losing work vs. doing it twice (reliable queues)
  With LPOP, the item leaves the queue before the work is done, so a worker
  crash loses it (at-most-once). I came up with the idea myself: keep a "being
  worked on" list and re-queue items that sit there too long. That's the
  standard reliable-queue pattern. The catch is that "copy, then pop" as two
  steps has the same gap as the original bug, so you use LMOVE, which moves the
  item atomically. You acknowledge with LREM, and track claim times in a
  sorted set so stuck items can be re-queued. Redis Streams with consumer
  groups have this built in. Re-queuing means a slow job might run twice
  (at-least-once). That's safe here because classification is idempotent: the
  same image always writes the same result.

● Here's the same idea as a restaurant kitchen.

  The setup

  - The queue is the rail of order tickets.
  - A worker is a cook.
  - LPOP is a cook pulling a ticket off the rail.

  The problem: losing work

  With LPOP, the cook pulls the ticket off the rail and puts it in his pocket,
  then starts cooking. If he faints halfway through, the ticket is in his
  pocket. It's no longer on the rail, so no other cook knows the order exists,
  and the customer never gets food.

  That's "at-most-once": each order gets cooked once or not at all.

  The fix: a "cooking now" board

  Instead of pocketing the ticket, the cook clips it onto a "cooking now" board:
  1. Take a ticket: move it from the rail to the board.
  2. Finish cooking: throw the ticket away. That's the "acknowledge" step
     (LREM).
  3. The manager checks the board every so often. If a ticket has been there 10
     minutes with no food, the cook probably fainted, so the manager puts the
     ticket back on the rail for another cook.

  Now an order can't disappear. Either it's on the rail, or it's on the board
  where someone is watching it.

  To know how long a ticket has been on the board, write the time on it when
  it's clipped up. That's what the "sorted set with timestamps" does.

  The catch: one motion, not two

  Moving the ticket has to be one motion. If the cook first copies it onto the
  board and then takes it off the rail, another cook could grab the same ticket
  in between. That's the same gap as the original bug. LMOVE does "off the rail
  and onto the board" in a single motion that nobody can interrupt.

  The new downside: sometimes cooking twice

  What if the cook didn't faint and was just slow? The manager sees the old
  ticket, puts it back on the rail, and a second cook makes the same dish. The
  order gets cooked twice.

  That's "at-least-once": every order gets cooked, but some might get cooked
  twice.

  Is cooking twice bad?

  It depends on the job:
  - In this project, it's harmless. Classifying the same castle photo twice
    gives the same answer ("church, 0.41"), written to the same key. The second
    copy overwrites the first with identical data. A job you can safely repeat
    like this is called idempotent.
  - For charging a credit card, it would be bad. Doing it twice charges twice.
    That job is not idempotent and needs extra protection, such as checking "did
    I already charge for this order ID?"

  Redis Streams

  Redis has a feature called Streams that includes the board, the throw-away
  step and the manager's checks, so you don't have to build them yourself.

  One-sentence version

  Without a "cooking now" board, a crashed worker's job disappears. With one,
  nothing disappears, but a slow job might get done twice, which is fine when
  doing it twice gives the same result.

● Idempotent (eye-dem-POH-tent) means doing it twice has the same effect as
  doing it once.

  Everyday examples:
  - ✅ An elevator button. Press "3" once or five times, and you still go to
    floor 3. Idempotent.
  - ✅ Setting your thermostat to 70°. Set it once or ten times, and it's still
    70°. Idempotent.
  - ❌ "Add $20 to my account." Do it twice and you've added $40. Not
    idempotent.
  - ❌ "Turn the thermostat up 2°." Twice gets you +4°. Not idempotent.

  In Redis terms:
  - SET key "church" is idempotent. Run it twice and the key still says
    "church."
  - RPUSH queue item is not. Run it twice and the item is in the queue twice.

  In this project, the worker classifies an image and runs SET <uuid> <result>.
  If a slow job gets re-queued and runs again, it writes the exact same result
  to the exact same key. Nothing changes, so running it twice is harmless.

  Rule of thumb: "set it to X" is usually idempotent. "Add X" or "do X again"
  usually isn't.
